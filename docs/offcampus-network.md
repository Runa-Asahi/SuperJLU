# 校外连接、WebVPN 与浏览器选择

## 复现与判断

用户反馈：手机家庭 Wi-Fi、移动流量，以及电脑连接手机热点时，课表、成绩、学业均无法同步；重新登录在 CAS 入口出现 `SSL: UNEXPECTED_EOF_WHILE_READING`。设置中的旧登录标记并不能证明当前网络可达。在外部浏览器登录 WebVPN 后，原程序同步仍未恢复。

原版本来就能发送微信验证码，故障点是输入并提交验证码之后。“能发送验证码”不是修复进展或登录成功的证据。验证 POST 与后续教务回跳现已分开处理，失败提示标明阶段和实际目标主机，避免回跳失败也错误地标成 CAS 连接失败。

该异常发生在 HTTPS 通信阶段，不能据此判断密码错误或会话过期。匿名探测成功也不等于已经登录、能够查询个人数据。用户反馈的跨网络现象须与自动测试、匿名探测、真实账号验收分别记录。

学校 OA（`oa.jlu.edu.cn`）可经校园网或学校 VPN 访问，不能表述为“只能校园网直连”。应用内选择「校外 WebVPN」后，教务与 OA 通知同步均走应用内 WebVPN 路由；在浏览器中登录 WebVPN 可访问原站，但不会把浏览器会话传给程序。软件学院和计算机学院官网通知独立直连。此前对照中 VPN OA 代理曾报 WinHTTP 12029，校外真实会话验收仍待完成。

## 地址与端口

| 用途 | 地址 | 说明 |
| --- | --- | --- |
| 桌面界面 | `127.0.0.1:8765`，忙时随机端口 | 本机服务，与学校 HTTPS 出口分开 |
| Android 界面 | `127.0.0.1:随机端口` | 应用内部服务 |
| 统一认证 | `cas.jlu.edu.cn:443` | 登录、认证和换票 |
| 教务 | `iedu.jlu.edu.cn:443` | 课表、成绩、考试和学业共用 |
| WebVPN | `vpn.jlu.edu.cn:443` | 独立的应用内会话 |
| 学校 OA | `oa.jlu.edu.cn:443` | 可经校园网或学校 VPN 访问；应用内 WebVPN 模式下同步走 VPN |

Android 原先用旧域名 `jwxt.jlu.edu.cn:80` / OA 的 TCP 80 判断校园网，既不对应实际教务入口，也不验证 TLS。现在检查实际教务 HTTPS，OA 单独提示。端口可连接、HTTPS 可用、账号已登录和业务请求成功是不同状态。

## HTTPS 恢复

`network.SchoolHTTPSHandler` 保留 urllib 的 Cookie、HTTP 状态和重定向管线，在单次 HTTPS 跳转内处理被 `URLError` 包装的 SSL 中断：

- 学校站点的安全 GET/HEAD 最多恢复一次，传递剩余超时，不重复完整登录链。
- Windows 兼容通道使用进程内 WinHTTP/Schannel；Android 使用系统 `HttpURLConnection`。保持 HTTPS、证书及主机名校验，不降低 TLS 安全级别。
- 在 Windows / Android 上，统一认证、教务、VPN 从首个请求起统一使用系统通道，避免 GET 能成功但验证码 POST 仍使用另一套 TLS。其它学校站点保留安全 GET 的有限恢复。
- 系统通道只处理单跳，保留多个 `Set-Cookie`，由 urllib 继续管理重定向和 Cookie 域名/路径。
- 某主机的 GET 成功切换系统通道后，后续 POST 首次即用该通道；POST 失败不自动重发。
- TPASS 的 `recheckcode` 虽是 GET，却会发送验证码，必须排除；退出登录、带单次 `ticket` 的请求也不重放。
- 证书验证错误不触发回退；其它平台仅对安全请求重试一次。
- 网络错误返回 502 与 `error_kind`，保留缓存，不伪装成 401 会话过期。错误提示只含主机/端口，不回显 URL 查询参数、Cookie、票据、密码或验证码。

本地匿名对照曾出现 Python 对 VPN 报 SSL EOF，而 WinHTTP 能取得正常 302；CAS 在部分检查中两种通道均成功。因此兼容通道有实际恢复证据，但不能据此宣称手机、CAS 和所有业务同步均已验收。

## 应用内 WebVPN

按用户确认的学校新方案，教务仅支持校园网内直连，校外需要学校 VPN。已撤回实验性的自动连接逻辑，统一在「更多 → 登录」中手动选择「校园网直连」或「校外 WebVPN」。校园网内使用直连；家庭 Wi-Fi、手机流量和热点选择校外 WebVPN，通过一次认证建立应用内 VPN 并验证教务，无需先登录直连教务。

不再探测并自动改道，也不在请求失败后切换通道重发。直连登录明确使用直连客户端；校外登录先确认 VPN，再验证教务。仅在认证成功、会话保存完成后切换所选通道；取消、失败或保存失败保留原通道和本地数据。

原有手动设置保持不变。遇到已退役的自动设置时，若存在应用自己的 VPN 会话则恢复为手动 VPN，否则恢复直连；迁移过程不联网、不清除账号或会话。旧自动切换接口已移除。独立的「连接检测」仍只检测直连，不修改通道或账号状态。当统一认证与 WebVPN 门户可达、但教务 TLS 失败或 OA 超时（常见校外直连缺口）时，结果区会提示到「更多 → 登录」选择「校外 WebVPN」；该提示不声称本机已验收 OA 经应用内 WebVPN。

统一登录卡片保留；「当前连接方式」使用主题色背景、边框与大号粗体，最近成功连接单独显示，避免把待选择的方式误认为已生效通道。VPN 成功但教务未验证时保留明确提示，VPN 返回自己的 CAS 登录页不会误报教务账号过期。换网后用户手动选择对应方式，学校要求二次认证时仍需完成验证码。

教务查询、同步的网络或接口错误向界面返回简短提示，引导检查网络或到「更多 → 登录」切换登录方式，不输出长串尝试地址。空教室页保留上次结果，并显示持续可见的失败提示及「检查登录方式」按钮；按钮只导航，不自动切换。真实会话过期仍返回 401；输入校验、证书错误与登录认证阶段的诊断分别保留，不把它们统一解释成换网。底层 CLI 的详细诊断仍保留。

应用内连接过程：

1. 选择「校外 WebVPN」后使用同一个登录按钮进行密码/验证码认证；VPN 与教务使用不同的 service，内部可复用本应用已完成的统一认证，不把教务登录当成 VPN 已登录。
2. 使用学校公共入口的真实 CAS service `https://vpn.jlu.edu.cn/login?cas_login=true` 换票。
3. 确认 VPN 门户已离开登录页后，加密保存应用自己的 VPN Cookie，再启用教务通道；失败不自动启用。
4. 同步转换教务传输 URL、业务 Referer 和每一次回跳。CAS 保持直连，票据必须签发给**原始教务 service**，再通过 VPN 传输去消费；把 service 改成代理 URL 会被教务拒绝并造成认证循环。新的 CAS 会话优先于旧教务缓存中的同域 Cookie。
5. 学校 OA 与教务一并按所选通道换路；学院、选课和其它站点保持原路由。回到校园网后可选择「校园网直连」重新登录切换。

2026-10-18 对照学校未登录公共入口，发现主机编码参数已与旧的 `Didida1127Didida` 不同。新参数已用公开 CAS 域名及实际跳转向量校验，历史参数继续支持解码。如果学校再次调整参数，需要重新核对公共入口，不能把编码错误误判为登录过期。

外部浏览器状态与应用内连接分别标注；没有应用内会话时显示“浏览器状态未知”，不声称用户未在浏览器登录。不得抓取系统浏览器 Cookie 或凭据。

二次认证已签发教务票据、但直连回跳失败时，只加密保存已验证的 CAS 会话，不谎报教务登录成功。界面可选择经应用内 WebVPN 继续，无需重新发验证码。

本地热点对照：教务 TCP 443 能连接，但 TLS 在 Python、Windows 系统 HTTPS、curl 中均超时；使用修正后的应用内 WebVPN 已完成课表、成绩、考试、校历、节次、官方绩点、学业完成与培养方案的真实会话同步。这不代表学校 OA 或 Android 真机已验收。

## 学校 OA、学院通知与选课

学校 OA 刷新失败时保留缓存，并说明可通过学校 WebVPN 在浏览器访问原站。接口区分 `browser_vpn_supported` 与 `app_vpn_supported`：后者仅在当前通道为应用内 WebVPN 且已有 VPN 会话时为真，避免把原站支持 VPN 等同于本次同步已走应用内 VPN。通知页保留学校 WebVPN 入口。学院栏目分别请求官网，单个来源失败不推断校园网限制，也不阻止其它栏目更新。教务恢复校内网标记和 VPN 入口；选课保持可直接访问。

本轮 OA 核对：本机直接读取 OA 列表成功，返回 HTTP 200、可解析 30 条通知；不记录或输出标题和正文。相同环境下 VPN 门户及其 OA HTTPS/HTTP 代理地址均报 WinHTTP 12029（连接失败），故不能把本轮结果写成 OA 已通过 VPN 验收。应用内现已支持按通道代理 OA，但校外真实会话仍须分别验证。学校[官方 WebVPN 使用指南](https://nic.jlu.edu.cn/info/1018/2148.htm)说明其用于校外访问校内网站。

## Android 外部浏览器

用户在 OPPO Find X8 Ultra / ColorOS 16 / Android 16 上反馈：local.19 点击外链完全不出现选择窗口，直接打开默认浏览器，随后记忆的仍是默认浏览器。这是该真机的实际失败记录。之前的 JVM 仅确认 ACTION_CHOOSER 和回调代码，不能证明系统会列出其它浏览器；不要继续把这个结果写成已解决。

local.20 的系统应用选择又列出了全部应用，用户明确要求移除此实现。local.21 删除指定浏览器的全部实验算法，只保留「外部浏览器」UI 卡片、禁用的更换按钮和 `superjlu://browser-settings` 原生接口占位。直接调用该接口只提示暂不可用。正常外链使用普通 ACTION_VIEW 交给系统默认浏览器，不读取旧偏好、不扫描应用、不显示应用列表、不请求全局设置变更。

## 验证要求

Python 回归覆盖包装的 TLS EOF、证书错误、恢复次数、POST/验证码/票据不重放、Cookie/重定向、脱敏错误、WebVPN 路由与失败保护、匿名检测、选课旧覆盖和通知来源独立性。Android API 28 / 35 的 JVM 回归覆盖文件选择、禁用浏览器入口的边界，以及单跳 HTTPS 的请求体、多个 Cookie、错误响应与连接释放。

换网提示回归使用虚构的长串 HTTP 404、TLS 中断、超时与过期状态，确认提示简短、缓存不变、正常校验错误不被覆盖。浏览器部分当前只验证禁用后的边界：忽略实验版偏好、外链使用正常系统路由、接口占位不调用选择器或全局设置、不支持的链接被拒绝、缺少处理器时提示失败。后续实现及真机要求单独列入 TODO，不能以占位回归宣称选择功能已经完成。

最终占位版验证：Python 350 项通过，三组 Node 回归通过，Android API 28 / 35 共 38 项 JVM 测试通过；debug 构建与 Lint 完成（0 错误、8 条既有警告）。390 像素宽的隔离预览确认连接状态醒目且无横向溢出，模拟第二次查询失败时保留首次结果，检查登录方式按钮可定位到登录卡片。local.21 安装包已核对版本、签名及打包源码，确认旧选择和记忆逻辑已删除，按钮处于禁用状态，安装包不含真实账号或成绩缓存；上述结果不代表 Android 真机端到端验收。

回退验证覆盖手动配置与旧自动配置迁移、直连失败不自动探测或切换、移除自动切换接口、选择/取消不改变生效通道、认证和保存失败保留旧通道，以及 VPN 过期不误报教务过期。历史真实会话曾完成全部 8 项教务同步，不据此推断学校当前的校外直连策略。恢复后的 APK 使用更高版本号，方便覆盖自动版并保留 Android 私有数据；分发目录中的 local.12～local.14 自动版安装包移除。

匿名检测不读取真实会话。实际登录由用户在本地界面完成，需要时先发 Windows 提示，不在聊天中索要密码或验证码。发布前仍须分别在真机、家庭 Wi-Fi、流量、电脑热点及校园网验证；不能用 JVM 测试或桌面预览代替 Android 端到端验收。
